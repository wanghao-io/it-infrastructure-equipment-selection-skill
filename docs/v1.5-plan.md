# v1.5 Evidence-Gated Depth and Usability Plan

Status: implemented for v1.5.0
Baseline date: 2026-08-20

## Objective

v1.5 is a bounded depth, evidence and usability release. It must make the existing engineering rules easier to apply while preserving the sequence:

> requirements → architecture → sizing → Mandatory technical fit → evidence → price

It is not a product-database, crawler, stateful project application or broad API release.

## Baseline and external-review corrections

The plan is based on the v1.4.3 repository, not earlier v1.3-era descriptions.

| External observation | Decision | Current evidence / reason |
|---|---|---|
| Firewall, HCI and domestic/Xinchuang references are uneven in depth | Accept, P0 | The references are currently 15, 26 and 20 lines. HCI has a strong deterministic core, but its method and field semantics are still thin. |
| Add real procurement and operational evidence chains | Accept as a claim-gated program | Existing public retrospectives are correctly limited to `design-baseline-only`. Higher-stage evidence must come from authorized real artifacts and must never be manufactured for a release. |
| Bus factor 1 is the main sustainability risk | Accept, strategic | Governance, roles and a release-rehearsal procedure already exist; a real second human and an auditable rehearsal record do not. |
| `SKILL.md` is about 500 lines and needs another trigger table | Already resolved | `SKILL.md` is a compact Router with precedence, route tables and fallbacks. Keep the semantic and 300-line ceiling tests; do not impose a minimum or compress mechanically. |
| Tool exposure needs classification | Already resolved | All 24 scripts are catalogued as `public-run`, `public-gated`, `lifecycle`, `deferred` or `internal`; the CLI already states that it does not perform live research. |
| The project has five Schema contracts | Outdated | There are seven contract families and nine named supported versions/examples, including v2 price evidence and retrospective contracts. |
| Add a one-stop CLI workflow | Reject in that form | The Agent Router is the workflow orchestrator. Deterministic CLI commands must remain narrow and must not impersonate research, architecture or procurement judgment. |
| Add arbitrary `custom_fields` to core contracts | Reject | Strict unknown-field rejection is intentional. Private additions use a namespaced manifest and adapter; a future shared extension requires a new versioned contract, not an unbounded escape hatch. |
| Add a public product/price database or crawler | Defer | It would add freshness, neutrality, privacy and maintenance risks before external demand and stewardship exist. |
| Add industrial calculators, Web UI, MCP, HTTP API or configuration memory | Defer | New state and interfaces need repeated user evidence, contracts, privacy analysis and maintainers. Reference methods and current guarded commands come first. |

## Invariants that v1.5 must preserve

- Keep all twelve invariant IDs and their behavior in `SKILL.md`.
- Keep missing Mandatory facts `CONDITIONAL`; do not convert uncertainty to PASS to make a helper runnable.
- Keep technical eligibility ahead of price, score and TCO for every product class.
- Keep private raw quotations, customer identifiers, contacts and credentials outside code repositories.
- Keep v1 Schema contracts compatible and migrations non-destructive.
- Keep Agent research distinct from deterministic calculation and contract validation.
- Keep the Router below its tested 300-line progressive-disclosure ceiling; do not impose a minimum line count.

## P0 workstream 0 — Correctness and contract repair

Complete these gates before exposing additional CLI commands:

- freeze decision scope, product class and baseline amount/currency for budget revision; reject conflicts and cross-currency comparison;
- add `server-rfq-v2` for the exact procurement object and keep v1 claims coarse;
- preserve UNKNOWN in architecture evaluation instead of defaulting missing facts to false/one;
- reject NaN/Infinity, validate reserve factors and round indivisible resources upward;
- make the public scenario-template contract executable through the guide;
- keep HCI arithmetic PASS separate from final-design eligibility;
- remove example architectures that default HCI/firewall/DMZ without explicit triggers.

## P0 workstream 1 — Domain depth and fail-closed guidance

### Shared reference acceptance contract

Each of the three strengthened references must contain:

1. triggers and explicit non-applicable conditions;
2. required inputs, assumptions and TBD fields;
3. a sizing or verification sequence;
4. Mandatory PASS / CONDITIONAL / FAIL gates;
5. evidence and lifecycle requirements;
6. a stable output field list;
7. at least one positive example and two negative examples;
8. its relationship to scripts, Schema, licenses, BOM scope and capability fallback;
9. an explicit rule that unknown evidence cannot become technical PASS;
10. an explicit rule that price cannot rescue technical failure.

Line count is not an acceptance criterion. Depth is accepted only when decisions and failure behavior are testable.

### Firewall sizing

Expand `references/firewall-sizing.md` to cover:

- whether a security boundary is justified before choosing an appliance;
- peak and growth traffic, north-south/east-west flows and encrypted-traffic ratio;
- stateful, firewall, NGFW, IPS, threat-protection and SSL-inspection metric separation;
- concurrent sessions, new sessions per second, VPN users/tunnels, interfaces and routing mode;
- single-survivor sizing for HA instead of summing two appliances;
- IPS, AV, application control, URL, SSL, VPN, logging, HA and subscription/license scope;
- current official evidence, configuration scope, lifecycle, acceptance tests and upgrade triggers;
- standard output: requirement, evidence metric, candidate metric, status, `eligible_for_pricing`, TBDs and risk.

Required negative cases:

- 10 GbE ports and high stateful throughput do not satisfy a higher threat-protection requirement;
- an SSL-inspection requirement without corresponding performance evidence remains `CONDITIONAL`;
- two HA members that pass only when their throughput is added together fail single-survivor sizing;
- a bare appliance without required security subscriptions cannot anchor the complete budget;
- an isolated OT network does not acquire a firewall merely because the category exists.

Do not add a universal firewall performance formula in v1.5. Vendor test profiles are not interchangeable, and a generic discount factor would create false precision.

### HCI design

Expand `references/hci-sizing.md` while retaining `hci-failover-v1` compatibility:

- add a decision tree comparing standalone, traditional virtualization/shared storage and HCI;
- cover node, disk, link, switch, rack/site and maintenance-plus-failure scenarios;
- define quorum/witness, failure domains, replicas/erasure coding, rebuild capacity and rebuild window;
- separate CPU overcommit, platform overhead, memory reserve, effective storage, IOPS and east-west network calculations;
- state that three nodes may be common but are never the default or a universal minimum;
- separate arithmetic PASS from support-matrix, license, failure-domain and operational-readiness evidence;
- explain the exact v1 meaning of `usable_storage_tb` and warn against filling evidence booleans with `true` when evidence is unknown.

Required negative cases:

- any CPU, memory, effective-storage, IOPS or network shortage fails N+1;
- adequate arithmetic with unknown quorum, failure-domain or support evidence remains `CONDITIONAL`;
- insufficient rebuild space cannot pass;
- score or lower TCO cannot rescue a Mandatory failure;
- a successful HCI calculation cannot be used to prove that the project needs HCI.

`hci-failover-v2` remains evidence-gated. Define it only after at least two materially different implementations demonstrate stable field semantics. A future v2 should represent `PASS`, `FAIL` and `UNKNOWN` evidence separately from calculated capacity.

### Domestic/Xinchuang compatibility

Replace brand-list thinking in `references/domestic-platforms.md` with a versioned compatibility chain:

```text
CPU ISA and exact model
→ firmware/BMC
→ OS version and kernel
→ virtualization/container layer
→ database and middleware
→ application/SCADA version
→ PLC/OPC/special drivers
→ NIC/RAID/GPU/USB dongles
→ backup/security/management agents
```

For every Mandatory link record the exact version, requirement source, official support matrix/certification/PoC evidence, evidence date and stage, status, blocker, owner and validation action.

Required negative cases:

- a domestic CPU and OS with an unsupported SCADA/PLC driver fail the chain;
- a certified OS/database pair with an unknown application version remains `CONDITIONAL`;
- a generic “fully compatible” marketing page without versions or tests cannot produce PASS.

Tender output must remain capability- and evidence-based. Do not create a permanent vendor ranking or treat a brand name as proof of compliance.

## P0 workstream 2 — Guarded CLI and failure contract

Add dedicated fail-closed subcommands only for capabilities already classified `public-gated`:

- `guide` — discovery only; never selects architecture;
- `server-quotes validate|compare` — validates supported versions, but exact comparison requires `server-rfq-v2`; v1 remains coarse validation only;
- `price-evidence` — requires a supported strict version and exposes no legacy bypass;
- `migrate` — reports first, preserves the source and refuses destination overwrite.

Document a common command failure contract for:

- invalid or unknown Schema/version;
- missing Mandatory evidence;
- technical FAIL or `CONDITIONAL`;
- insufficient independent price evidence;
- mixed decision scope, currency or market basis;
- unresolved/TBD cost;
- overwrite refusal and unsupported capability.

The contract must define exit status, stdout/stderr behavior, machine-readable status and whether any output artifact may exist after failure. Normal user errors remain concise; debug traces remain opt-in.

## P0 workstream 3 — Decision summary without information loss

Add an optional summary layer ahead of the existing detailed profiles:

1. conclusion and current decision state;
2. Mandatory blockers and facts that can be frozen now;
3. decisions awaiting evidence;
4. the 3–7 highest-value confirmations;
5. assumption/evidence ledger;
6. links or appendices containing the unchanged calculations, BOM, evidence and acceptance detail.

Do not replace the existing `quick-selection`, `internal-review`, `procurement-rfq`, `detailed-design`, `compliance-check`, `bom-budget` or `budget-revision` contracts. The summary changes presentation, not engineering depth.

Add one synthetic one-page end-to-end example showing natural-language input → routed decisions → concise summary → selected detailed artifacts. Do not present synthetic prices as current market evidence.

For references longer than 100 lines, add a compact table of contents and a decision checklist or quick path where it reduces unnecessary loading. Do not duplicate normative rules between `SKILL.md` and references.

## P1 workstream 4 — Real-project evidence and claim gates

Extend `references/real-project-validation.md` with a private-project-to-public-retrospective checklist:

- identify artifact owner and publication authority;
- inventory design, quotation, award, settlement and measurement sources;
- normalize technical and commercial scope before comparing amounts;
- record hashes/provenance privately without publishing sensitive originals;
- remove customer, supplier-contact, IP/VLAN, CAD/location and contract identifiers;
- validate the supported retrospective contract and semantic stage rules;
- obtain a second review of anonymization and claim level;
- publish only the minimum facts needed to reproduce the engineering lesson.

Evidence stages are claim gates:

- `design-baseline-only` supports workflow/design lessons only;
- `current-quotes` supports dated quotation-range observations only;
- `award-record` or `settlement-record` is required before procurement-forecast accuracy claims;
- `operational-measurement` is required before reliability, power or capacity-in-operation claims.

Target at least one authorized anonymized `current-quotes`-or-later retrospective for v1.5. If no publishable higher-stage artifact exists, v1.5 may still ship, but its Release Notes must explicitly state that market, settlement and operational accuracy remain unvalidated. Two or three complete chains remain a post-v1.5 evidence objective, not an invitation to fabricate data.

## P1 workstream 5 — Repeatable evaluation and property tests

Expand the evaluation set to at least ten independent scenarios covering:

- small IT without unjustified HCI/HA;
- SCADA historian and OT remote control;
- existing-budget downward pressure;
- HCI N+1 plus incomplete TCO;
- firewall threat/SSL/HA metric mismatch;
- domestic-platform compatibility-chain failure;
- no-web and reduced-host capability fallback;
- cross-region price evidence and delivery/tax ambiguity;
- private-extension and sensitive-data boundaries;
- invalid Schema, mixed scope and overwrite refusal.

Keep two evaluation surfaces distinct:

1. CI validates fixtures and executes deterministic gates with stable assertions.
2. Fresh-agent evaluation records raw prompt, capability set, sanitized output, blocking criteria and reviewer verdict.

Do not claim that ordinary unit CI deterministically reruns an Agent answer. Preserve the independent evaluation record instead.

Add seeded property/boundary tests for price normalization and budget revision, including:

- input permutation does not change the decision;
- multiple quote IDs from one normalized supplier remain one independent source;
- invalid/TBD costs never become zero;
- mixed decision scopes, currencies or incompatible market bases fail closed;
- no weak-evidence combination can lower a protected baseline;
- migration never invents PASS, Verified, zero, current date or supplier identity.

Extend v2 negative fixtures for decision-scope errors, evidence-stage contradictions and scope-normalization omissions. Prefer deterministic seeded tests before adding a new fuzz dependency.

## P1 workstream 6 — Region, tax and delivery context

Add an explicit research context for `CN`, `APAC`, `EU`, `NA` or a named local market:

- market/ship-to region and evidence-source jurisdiction;
- currency and conversion date/source when conversion is necessary;
- tax inclusion/exclusion and the party responsible for tax treatment;
- freight, duties, Incoterms/delivery scope, warranty territory and support availability;
- explicit rejection of cross-region listings that are not commercially comparable.

China-market channel guidance remains first-class, but it must be labeled as such. Other markets require local evidence and may degrade to `Needs confirmation` when suitable sources are unavailable.

Do not embed default tax rates or treat a region code as tax advice. Rates and applicability are time-, entity- and transaction-dependent facts.

## P1 workstream 7 — Community and bus-factor actions

Create a first-contribution pack as bounded public Issues:

1. one thin-reference improvement with source and negative-test requirements;
2. one deterministic boundary/Schema negative fixture;
3. one reproducible documentation or CLI usability defect.

Each Issue must name the relevant files, non-goals, expected tests and definition of done. A reviewer path should start with reproducing an Issue and reviewing its evidence/test change before any repository access is considered.

Before v1.5 usability claims, record:

- at least two non-maintainer artifact or workflow reviews; and
- at least one non-maintainer read-only release rehearsal using the documented runbook.

These records improve reviewability but do not change the reported bus factor. Report bus factor 2 only when the existing governance access and recent independent release-capability conditions are actually met.

## P1 workstream 8 — Private extension and security usability

Reaffirm the existing three-layer boundary for downstream/private use:

```text
public core rules, contracts and tests
← minimized validated projection
private namespaced adapter and templates
← access-controlled raw quotations and project data
```

Add a synthetic mapping example that strips supplier-declared decision fields and converts a private source into a supported core contract. Run the complete public test suite plus extension-specific tests when syncing a private extension.

Do not add `custom_fields` to frozen contracts. If several independent extensions demonstrate the same portable field, propose a versioned core or extension contract with migration and negative tests.

Add a pre-publication/output sanitization reminder for customer names, supplier contacts, IP/VLAN values, precise locations, CAD/process details and credentials. Tender parameters remain vendor-neutral unless a restriction is documented as Mandatory.

## Explicitly deferred from v1.5

- permanent vendor/model rankings;
- a public product, compatibility or price database;
- automatic price crawling, purchasing or supplier outreach;
- automatic discovery of private files, environment variables or adjacent repositories;
- arbitrary core `custom_fields`;
- a broad HTTP API, Web UI, MCP wrapper or stateful configuration memory;
- GitHub Pages as a release blocker;
- new calculators without repeated real-project demand and stable input semantics;
- a universal firewall degradation formula;
- `hci-failover-v2` before cross-implementation evidence exists;
- hard-coded tax rates or legal/compliance conclusions from region alone.

## Milestones and dependencies

| Milestone | Deliverables | Depends on |
|---|---|---|
| M0 — baseline lock | Preserve invariants, v1 contracts, Router range and existing tests | v1.4.3 |
| M1 — domain depth | Firewall, HCI and domestic references plus negative fixtures | M0 |
| M2 — safe usability | Guarded CLI commands, common failure contract, decision summary and demo | M0 |
| M3 — evidence/eval | Ten scenarios, seeded properties, retrospective export checklist and truthful evidence records | M1, M2 |
| M4 — community verification | First-contribution pack; external reviews/rehearsal gate only external-usability and bus-factor claims | M1–M3 artifacts |
| M5 — release | Full CI, package/Agent Skills compatibility, current-only notes and clean archive | M1–M3 |

M1 and M2 may proceed in parallel. A higher evidence-stage retrospective depends on authorized artifacts, not on code completion.

## v1.5 release gate

Do not publish v1.5 until all applicable gates pass:

- all 138 v1.4.3 baseline tests and every new v1.5 regression pass on the full supported OS/Python matrix;
- the twelve Router invariants, route reachability and progressive-disclosure bounds remain intact;
- the three domain references meet the shared acceptance contract and their negative cases fail closed;
- every new CLI command performs mandatory preflight, has no silent legacy path and refuses unsafe overwrite;
- deterministic failure output contains no partial success result;
- at least ten independent scenarios contain no blocking violation;
- every public field claim matches its actual design/quote/award/settlement/operational evidence stage;
- private or supplier-controlled data cannot self-declare PASS, eligibility or evidence strength;
- full cross-platform validation, staged `gh skill publish --dry-run`, clean archive installation and checksum generation succeed before Release publication.

An authorized higher-stage retrospective strengthens v1.5, but absence of one must result in a narrower Release claim, never invented evidence.

Non-maintainer reviews and a release rehearsal are claim gates for external usability and bus-factor improvement. Their absence must not block a correctness/security release, but Release Notes must not imply independent adoption or stewardship.

## Success measures

v1.5 succeeds when:

- a new user can choose the correct route and obtain a concise decision without losing the audit trail;
- firewall, HCI and domestic-platform work fails safely on common metric or compatibility traps;
- guarded CLI users receive predictable, machine-readable failures;
- evaluation distinguishes deterministic regression from Agent judgment;
- private integrators can map data without weakening strict public contracts;
- external reviewers can reproduce a bounded task and a release rehearsal;
- no new feature makes current price, compatibility or field accuracy claims stronger than its evidence.
